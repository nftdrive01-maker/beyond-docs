# ネットワーク診断の判定仕様

ネットワーク診断の実測項目、採点条件、評価の有効性、保存と検証範囲をまとめます。操作方法と結果の読み方は[ネットワークを診断する](../guide/network-diagnostics.md)を参照してください。

このページは、提供された「BEYOND ネットワーク診断 仕様 v1.0.0」（2026年10月27日修正反映）に基づきます。v1.0.0は機能仕様の版であり、アプリ本体の版や採点エンジンの「BEYOND Network Quality Score v1.1」とは異なります。

## 1. 何を調べるか

登録済みブロックチェーンのREST情報、Catapult互換P2Pへの到達性、4地点のブロック提供、取得ブロックとREST基準の整合性を測ります。計測値に基づく**品質スコア**と、その評価を今も参照できるかを示す**評価の有効性**は別物です。ピア数、自己申告ロール、単一APIの成功だけでネットワーク全体を「正常」とは判定しません。

通常のBEYONDのオンチェーンデータ取得・検証は引き続きRESTを使用します。この診断のP2P通信は独立した検査です。特定のノード実装やプライベートネットワーク専用ではありませんが、P2Pパケットとブロック形式は現行のCatapult互換仕様を前提とします。

| 用語 | 意味 |
| --- | --- |
| 登録RESTノード | ネットワーク設定に保存されたAPI URL。自動修正後の最大20件など、設定側の数。 |
| RESTピア | 選んだAPIの `/node/peers` が返した自己申告の候補。 |
| 発見P2Pピア | REST候補を起点にP2P探索し、同じチェーンと判定して採用したノード。最大40件。 |
| 検査完了 | 接続不能を含め、該当ピアの検査を終えた数。4地点取得成功数とは異なる。 |
| 4地点 | 診断開始時の現在高をHとし、`floor(H/4)`、`floor(H/2)`、`floor(3H/4)`、`H` を選ぶ。各高さの下限は1。 |
| 未確認 | 応答がなく、提供不可と確定できない状態。0点の証拠としては扱わない。 |

**登録RESTノード20件と発見P2Pピア8件・40件は一致しなくて正常です。** それぞれ保存済みAPI、探索開始候補、今回見つかった検査対象という異なる母集団です。

## 2. 利用画面と実行手順

1. Blockchainsページで対象カードの**診断**を押します。既定の保存先ネットワークではなく、そのカードの設定を診断開始時に固定します。診断中に既定を切り替えても対象は変わりません。
2. モーダルにAPI接続、初期ピア、P2P探索、到達性、4地点履歴、集計・保存の6段階を表示します。探索中は母数が未確定なので完了率を出さず、対象確定後の検査件数から進捗を示します。
3. 完了後の結果はカードの**詳細 → 診断結果**で確認します。タブは「最新の診断」「過去との比較」「履歴推移」「ピア詳細」です。ピア詳細には分類フィルターがあります。
4. **診断を中断**すると進行中の通信を止め、`cancelled` としてその時点までの情報を保存します。API全滅やワーカー失敗は `error`、Web版のRESTのみは `rest-only`、デスクトップ版で最後まで終われば `complete` です。ローカル保存に失敗した場合は成功表示にしません。
5. 詳細画面の**チェーンを観測**は軽量なREST観測です。P2P検査も採点の再計算も行いません。結果は自動更新ではなく、詳細画面を開く際に保存済みデータから再表示します。

「診断完了」は処理終了を示すもので、全ピアの成功や全項目の採点成立を意味しません。6段目が完了色になるのは `complete` でローカル保存にも成功したときです。終了時の追加照合・保存中は中断を受け付けません。強制終了や画面プロセスの破棄では途中結果を保存できない場合があります。

進捗の「成功」は、到達性段階では接続成功、履歴検査段階では4地点の取得成功を示します。整合性検証の `verified` 件数とは異なります。

## 3. REST基本診断

ネットワーク設定の `defaultNode` と `nodes` を順に試し、最初に利用できたAPIを採用します。`/chain/info`、`/node/info`、`/network/properties` のgeneration hashとnetwork identifierが登録値に一致しなければ採用しません。1リクエストの通常タイムアウトは7秒です。

| 取得元 | 記録・計算する値 |
| --- | --- |
| `/chain/info` | 現在高、最終確定高・ハッシュ、Epoch、Point。開始時と終了時の2回を区別して保存。 |
| `/node/info`、`/network/properties` | APIノードの情報と自己申告ロール、チェーン識別、epoch adjustment、ブロック生成目標・voting set設定。 |
| `/blocks/{height}` | 最新を含む直近最大12ブロックの時刻、トランザクション有無、4地点の基準ブロック、確定ブロック。 |
| `/blocks/{height}/transactions?pageSize=1` | ブロック情報に件数がない場合だけ、空か非空かを補完。 |
| `/node/peers` | 最初のピア候補。処理中は最大200件、保存レポートのRESTピア配列は最大40件。P2P探索開始にはAPIノードと無作為に選んだ最大7件を使用。 |
| `/finalization/proof/height/{height}` | 可能なら確定証明を取得し、高さ・ハッシュを照合。取得成功は署名の暗号学的検証を意味しない。 |

平均ブロック間隔は、取得できた隣接高の**正の時刻差**の平均です。空ブロック率は、トランザクションの有無が分かったブロック数を分母、その中の空ブロック数を分子とします。標本不足なら未取得です。空ブロック率が高い、または空ブロックを生成しないことだけでは異常としません。ブロック時刻はネットワークのepoch adjustmentとブロックtimestampから復元します。ファイナライズ後の経過時間は**確定ブロックの時刻**から計算し、「確定高の進行を観測した時刻」と混同しません。

4地点の基準は主APIのブロックを取得し、登録された別のREST APIを最大2件照合します。別APIのチェーン識別、高さ、ブロックハッシュが合わない・取得できない場合は基準の信頼度を落とし、分岐やAPI遅延を考慮して未検証または競合として記録します。

## 4. デスクトップ版P2P診断

Web版ではブラウザーからCatapult P2Pへ直接接続せず、REST実測だけを `rest-only` として保存します。デスクトップ版ではElectronのIPCがOpenSSL対応Nodeワーカーを**診断実行時のみ**起動し、TLS 1.3のP2P接続を行います。サーバー証明書は一般のWeb CAではなく、取得した証明書の署名・期限・ノード公開鍵との対応を個別に確認します。接続とノード情報のチェーン識別も照合します。

TLSには診断実行時に生成する一時的なEd25519鍵と証明書を使用し、ユーザーのウォレット秘密鍵は使用しません。診断は読み取り操作であり、トランザクションの送信、ノードの自動修正、登録ネットワークの書き換えは行いません。

- 探索は幅優先、最大2段、40ピア、開始候補8件。公開鍵で重複排除します。接続・検査は最大4件ずつ並列です。
- 接続と通常P2P応答のタイムアウトは6秒、ブロック応答は20秒、受信パケット上限は16 MiBです。到達不能やTLS不一致は「接続不可」であり、直ちにノードの不正行為とはしません。
- 到達できたピアに最大4地点のブロックを実際に要求します。途中のエラーで残りの要求を打ち切る場合は、その地点を未確認のまま残します。高さごとに `取得成功`、`提供不可`、`未確認（タイムアウトや通信エラー等）` を区別します。「4地点すべて取得」は全履歴保持や将来の提供継続を証明しません。
- 公開鍵、ホスト・ポート、friendly name、version、roles、発見元、到達性、応答時間、検査時刻を保存します。名前・version・rolesは自己申告です。異なる公開鍵が別事業者・別設備を意味するとは限りません。

### P2Pブロック整合性

ワーカーはP2Pの**元バイト列**を解析し、ブロック長、予約領域、対応するブロック型・ヘッダー、トランザクションフレーム、高さ、network identifierを検査します。Catapult互換のGenesis・通常・Importanceブロックについて、署名・署名者公開鍵と所定ヘッダー領域をSHA3-256に入力してハッシュを再計算します。RESTのブロックもフィールドからヘッダーを組み直してハッシュを再計算し、RESTの `meta.hash` と合った基準だけを信頼します。さらにP2Pハッシュと前ブロックハッシュを基準と照合します。

| ブロックの整合性状態 | 意味 |
| --- | --- |
| `verified` | 対応形式の構造・高さ・ネットワークとヘッダーハッシュを確認し、信頼できるREST基準と一致。 |
| `mismatch` | 検証済みの不一致または不正な構造。採点上の不一致として数えるには、信頼できる基準との比較が別途必要。 |
| `unverified` | 未対応形式、確定前の分岐候補、あるいは必要な検証が終わらない状態。 |
| `reference_unavailable` | P2Pブロックは取得できたが、比較できる信頼済みREST基準がない状態。 |

整合性スコアに使う比較は、**確定済みの基準**、または**複数RESTが同じブロックで一致した基準**に限定します。未確定高での差異は分岐の可能性を残し、不正と断定しません。確定済みブロックとの差異でも、基準APIの問題やネットワークの状態を追加調査する必要があります。署名、Voting Set、全トランザクションの実行、チェーン全体の合意、事業者の独立性は検証範囲外です。

実装上のハッシュ入力は `bytes[8:104] || bytes[108:hashEnd]`（終端を含まないバイト範囲）です。`hashEnd` は通常ブロックで372、Genesis・Importanceで424。通常ブロックのヘッダー全長は376ですが末尾の予約4バイトはハッシュ入力に含めません。対応ブロックversionは1です。トランザクション本文のフレームは検査しますが、本文からトランザクションルートを再計算したり、署名を検証したりはしません。元バイト列は実行中の検証に使い、レポートにはハッシュ・判定・根拠を保存します。元バイト列そのものの保存・再配布機能ではありません。

## 5. 品質スコアの判定条件

各軸は0.00～5.00、未評価は `null` です。数値を出せないことを0点へ置き換えません。品質点は**今回観測できた対象の実測評価**であり、ネットワーク全体の保証ではありません。

| 軸 | 重み | 採点方法と必要条件 |
| --- | ---: | --- |
| 履歴可用性 | 35% | 各4地点で `成功 / (成功 + 明確な提供不可)` を計算し、その平均を5倍。全地点に少なくとも1件の判定済み応答が必要。通信エラー・未検査は分母に入れない。 |
| 履歴冗長性 | 25% | 4地点すべて判定済みのピアが `min(発見数, 5)` 件以上、かつ発見数の75%以上ある場合に採点。4地点すべて取得したピア数 `0 / 1～4 / 5～9 / 10～19 / 20～29 / 30以上` に対し `0 / 1.5 / 2.5 / 3.5 / 4.5 / 5.0` 点。 |
| P2P到達性 | 15% | 接続試験済みピア中の到達数を5倍した率。未試験ピアは分母に含めず、別途、発見数に対する試験カバー率を表示。試験済みが0なら未評価。 |
| ファイナライズ健全性 | 15% | 下記のSymbol Mainnet暫定基準が成立した場合のみ、進行50%・遅延30%・整合性20%のサブスコアを合算。 |
| データ整合性 | 10% | `5 × verified / (verified + mismatch)`。信頼済み基準との比較が5件以上、2高さ以上、`min(発見数, 2)` ピア以上、取得ブロックに対する比較カバー率75%以上などの条件が必要。基準RESTの競合や未確定分岐が残る場合は条件に従って未評価。 |

総合点は、**評価済み軸の `点数 × 重み` の和 ÷ 評価済み軸の重みの和**です。ただし履歴可用性・履歴冗長性・データ整合性の3軸は必須で、いずれか未評価なら総合点は**表示しません**。任意軸が未評価のまま総合点を出せた場合は「参考値」とし、採点カバー率（評価済み重みの合計）を併記します。ランクは A: 4.50以上、B: 3.50以上、C: 2.50以上、D: 1.50以上、E: 1.50未満です。画面の点数は小数第2位まで表示します。

履歴可用性・冗長性を採点するには `complete`、発見ピア1件以上、開始高から算出した相互に異なる4地点が必要です。古いGenesisを含む4地点セットは閲覧できますが、現行の25/50/75/100%採点条件に合わなければ未評価です。

整合性の「比較カバー率」の分母は、取得できたブロックまたは構造等の `mismatch` を検出した応答です。空応答・通信失敗を機械的に不一致へ加算しません。採点は上表の件数・高さ・ピア数・75%条件に加え、次をすべて満たす必要があります。

- 診断状態が `complete` である。
- 確定済み地点で基準REST間の競合がない。
- 確定済み地点との比較が1件以上あるか、基準REST間の競合が全地点でない。
- 確定済み地点との比較が1件以上あるか、未確定分岐候補がない。

### 画面の提供率と採点率の違い

履歴提供状況バーの分母は**全発見ピア**です。一方、履歴可用性の採点率は**応答を判定できたピア**を分母とします。例えば40ピア発見し、20ピアが4地点を提供、残り20ピアが通信不明なら、各バーの提供率は50%です。判定済み範囲の可用性は5.00点でも、冗長性の判定済み率が50%で75%条件を満たさず、総合点は未評価になります。灰色のバーは未確認を表し、中断直後などに全体が灰色でも直ちに描画不具合ではありません。

また「4地点取得成功」と `verified` は別です。未対応の互換ブロックを取得できた場合など、履歴の取得成功があっても整合性は未検証のことがあります。ピアの結果分類と整合性欄を合わせて確認します。

### ファイナライズ健全性の暫定基準

**Symbol Mainnetのみ**に適用します。generation hashとnetwork identifier `104`、`blockGenerationTargetTime = 30s`、`votingSetGrouping = 1440` の一致が前提です。これらはBEYONDの初期採点プロファイル条件であり、Symbol公式の障害基準ではありません。別チェーンや設定不明の場合は未評価で、低品質とは判定しません。

このプロファイルのgeneration hashは `57F7DA205008026C776CB6AED843393F04CD458E0AA2D9F1D5F31A402072B2D6` です。ネットワーク名が「Symbol Mainnet」であるだけでは適用しません。

- **進行（50%）**: 診断開始・終了で確定高が進めば5.0点。前回診断から20分以内の進行を、以前の確定ハッシュの再照合を含め確認できれば4.5点。確定高が変わらなくても、20分以上観測し、現在高が進み、最新ブロックが10分以内であるときに限り停滞の観測として0.5点。それ以外の短い無変化は未評価。
- **遅延（30%）**: 確定ブロックのタイムスタンプからの経過時間で、10分以下=5.0、10分超～20分以下=4.5、20分超～30分以下=3.5、30分超～60分以下=2.0、60分超=0.5点。タイムスタンプが取得できなければ未評価。
- **整合性（20%）**: 主APIの確定高・確定ハッシュ・確定ブロックが一致し、同じチェーンの別APIが少なくとも1件一致する必要があります。同じ確定高で合えば5.0点、異なる確定高でも共通の確定高のブロックが合えば4.5点。矛盾や照合不足はファイナライズ軸を未評価とします。証明取得は任意で、署名は検証しません。

終了時の別API照合は最大3件です。前回履歴から停滞を判定する観測間隔は**20分以上30分以下**で、確定高とハッシュが同一、以前の確定ハッシュの再照合成功、現在高の進行が必要です。今回の診断内で停滞を判断する場合は開始・終了間隔が20分以上であることが条件です。どちらも最新ブロックの経過時間が0～10分でなければ停滞点を付けません。基準のない私設チェーンにはこの時間条件をそのまま適用しません。`votingSetGrouping` は適用条件であり、その値だけから確定処理の実際の進行周期を断定するものではありません。

`最終確定高と現在高との差` だけでは採点しません。ブロック生成自体が停止しているネットワークで、確定高が動かない事実だけを停滞の証拠にもしません。

## 6. 評価の有効性と観測充足度

保存済み品質点は過去の実測値として残し、時間経過で勝手に減点しません。詳細画面の別ゲージ「評価の有効性」は**表示時の現在時刻**から再計算します。軸ごとの最終検証日時と期限は詳細で確認できます。新規レポートはP2P検査時刻とファイナライズ観測時刻を持ち、旧レポートは診断終了時刻へフォールバックします。

| 根拠 | 100%を保つ期間 | 鮮度低下 | 再診断・期限切れ |
| --- | --- | --- | --- |
| 完全診断、P2P・履歴・整合性 | 3日まで | 3日超～5日 | 5日超～7日は要再診断、7日超は期限切れ |
| REST API | 6時間まで | 6時間超～18時間 | 18時間超～24時間、24時間超は期限切れ |
| ファイナライズ採点根拠 | 10分まで | 10分超～20分 | 20分超～30分、30分超は期限切れ |

各根拠の鮮度は上の3境界間で `100 → 70 → 0%` と線形に下がり、その後0%です。各根拠を整数%へ丸めてから、**有効性% = round(0.85 × Σ(5軸の重み × 各軸の鮮度%) + 0.15 × REST鮮度%)** で集計します。未評価軸は加算せず、総合品質点が未評価なら有効性も0%です。必須軸が期限切れなら「期限切れ」、完全診断または必須軸が5日を超えた再診断帯なら「要再診断」。任意軸やAPIだけが古い場合は「鮮度低下」とし、ネットワーク障害とは呼びません。期限切れの根拠を含む品質点は「過去の実測値」として示します。

**観測充足度**は別指標です。直近30分を5分間隔の6枠とし、確定高・確定ハッシュを持つ同一チェーンの観測が入った枠数から `枠数 / 6` を算出します。同一枠の連続観測は1枠。全6枠かつ最初と最後が20分以上離れて初めて「観測充足」です。観測不足は監視密度の不足であり、ファイナライズ停止の判定ではありません。常時監視やバックグラウンド定期実行はありません。

採点カバー率、有効性%、観測充足度は別々の値です。観測充足度は有効性ゲージの数式へ直接加点しません。また有効性の5軸部分は未評価軸を除いた再正規化をしないため、例えばファイナライズ軸が未評価なら、他が新しくても100%にはなりません。

詳細の**チェーンを観測**は、押したカードの最大3つの登録APIの `/chain/info`・`/node/info`・`/network/properties` を試し、チェーン識別を確認して観測をローカルに記録します。REST根拠の鮮度と観測枠は更新できますが、**P2P・履歴・整合性・ファイナライズの品質サブスコアの検証時刻は更新しません**。軽量観測だけで古い総合品質点を新しい点に見せません。操作の流れは[ネットワークを診断する](../guide/network-diagnostics.md)を参照してください。

## 7. 保存、比較、互換性

| 保存先 | 内容 |
| --- | --- |
| `beyond_network_diagnostics_v1:{networkId}` | 直近の診断レポート。 |
| `beyond_network_diagnostics_history_v1:{networkId}` | 新しい順に最大20件。`networkId`とgeneration hashで読み分ける。 |
| `beyond_network_diagnostics_complete_v1:{encodeURIComponent(networkId)}:{generationHash}` | 同一チェーンの最後の完全診断1件。中断履歴などで20件の履歴から外れても保持。generation hashは大文字。 |
| `beyond_network_diagnostics_observations_v1:{encodeURIComponent(networkId)}:{generationHash}` | 軽量観測と完全診断の開始・終了観測。最大256件、読込時は直近7日分に限定。generation hashは大文字。 |

レポートには状態、開始・終了時刻、チェーン識別、REST実測、P2Pピア別の応答、警告、品質点と採点根拠、軸別の測定時刻を保持します。旧レポートに新しい項目がなくても読み込み、採点可能な生データは現行の採点ロジックで表示時に再計算します。したがって、将来の**採点ロジック変更時の履歴再表示値まで不変とは保証しません**。測定の生データと採点ロジック版をセットで解釈してください。期限切れ処理は保存済みの測定値や品質点を上書きしません。

最新の実行結果と品質評価の対象は分けます。最新が `cancelled`、`error`、`rest-only` の場合、実行結果はそのまま表示し、品質・有効性ゲージは同一チェーンの最後の `complete` を参照して対象日時を併記します。中断によって既存の評価を0%へ置き換えませんが、元の測定日時による鮮度低下・期限切れは継続します。完全診断が一度もなければ未評価です。新しい完全診断が完了した場合は、点数が低下した場合や採点不能の場合も新しい結果を採用し、良かった過去の点数だけを選びません。旧形式では履歴内の完全診断を読み、次回保存時に専用保存先へ引き継ぎます。すでに消えた履歴は復元できません。

比較・推移からは中断・失敗した診断を除外します。スコア差は採点版、generation hash、探索上限、発見数、検査数、4地点の条件が揃う場合に限り表示します。条件が違えば差分でネットワーク全体の変化を主張しません。履歴の保存容量はブラウザー/Electronのローカル保存領域に依存し、保存失敗は画面で通知します。

保存先はそのブラウザーまたはElectronプロファイルの `localStorage` です。別端末・別ブラウザーへ自動同期されません。保存領域を消去すれば診断履歴と観測記録も失われます。探索開始候補は無作為に選ばれるため、同じ上限で再診断しても検査対象の公開鍵まで同一とは限りません。

## 8. 環境・運用上の境界

- デスクトップのP2Pワーカーは診断時だけ起動します。中断、画面破棄、メインフレームのリロード・別文書への遷移、レンダラープロセスのクラッシュ、アプリ終了では中止要求を送り、応答しなければ5秒後に強制終了します。ページ内リンクやiframeの遷移だけでは中断しません。再読み込み後の画面へ旧ワーカーのイベントを渡さず、終了時にイベントリスナーも解除します。残る常駐診断サービスは設けません。開発版はOpenSSL対応のNode、配布版Windowsは同梱Node runtimeを使います。
- ワーカーは各ソケットを終了処理で閉じ、完了通知後に終了します。アプリの最終終了段階では残るワーカーを即時終了します。BEYOND-Coreのサービスを診断のために起動する仕組みではありません。
- REST接続は登録されたURLとそのネットワーク・ブラウザーの通信制約に従います。HTTPSページからHTTPノードへの接続、プロキシ、CORS、ノードの停止により取得できないことがあります。Web版はP2P到達性を評価できません。
- 探索は最大40件・2段に制限された標本です。ピア未発見、APIのピア一覧欠落、TLS非互換、ファイアウォール、時間切れはネットワーク全体の断絶を証明しません。
- 基準RESTとの一致はチェーン全体の合意証明ではありません。確定証明の暗号署名、Voting Set、全トランザクションと状態遷移、長期連続可用性、ピアの物理的独立性は対象外です。
- 品質点は判定条件を満たした観測範囲だけの値です。未評価・観測不足・期限切れを0点や悪意の証拠に読み替えないでください。
