# FAQ

BEYONDについてよくいただく質問と回答をまとめています。

## ブロックチェーンにすべて保存するのは無理では？

保存容量や処理能力に制限があることは、クラウド、データベース、ファイルサーバーなどを含む情報システム全般に共通します。ブロックチェーンに保存できる総データ量が、一律に小さいわけではありません。

実際に保存・取得・復元できる範囲は、保存媒体、ファイル形式、OS、ソフトウェア、通信経路、ネットワークの設計と運用によって決まります。個々のファイル、トランザクション、ブロックに適用される上限と、継続的に蓄積できるデータ総量は分けて考える必要があります。

フルオンチェーンの特性は、**データ実体と検証根拠を同じチェーン履歴に関連付けて保持できること**です。採用するかどうかは、必要な保存量に加え、取得可能性、独立した検証、障害からの復旧、公開範囲などの要件から判断します。詳しくは [フルオンチェーンとは](../concepts/full-onchain.md) をご覧ください。

## 容量が増え続けたらどうするのですか？

データの蓄積に応じた保存・処理資源の確保は、あらゆる保存方式に共通する運用課題です。フルオンチェーンでは、履歴を保持・同期するノードやアーカイブを含めて計画します。

チャンクに分割して記録すると、各チャンクやトランザクションの管理情報などの分だけ保存量が増えます。ファイルシステムやデータベースにも管理情報などの追加領域があり、こうした増加を含めて容量を計画することはデジタル保存全般に共通します。追加量の割合は保存形式や構成によって異なりますが、追加量があることと、保存できる総量の上限は別の問題です。

保存量の見通しに応じて、保存容量や通信・処理資源を増強し、保存モード、ノード構成、履歴の保持・提供方針を検討します。書き込み手数料の有無や額も対象ネットワークの設計・運用によって異なり、容量増加への対応を手数料だけで決めるものではありません。

BEYONDのデザイナーツールでは、チェーンの運用計画を事前に設計し、容量の概算見積もりや仕様書の作成を行えます。保存・検証に加え、運用開始前の計画立案にも活用できます。概算見積もりは計画の前提条件に基づく目安として扱い、実際の保存量や運用状況に応じて計画を見直します。

長期運用では、ネットワークの移行や [Chain Finalization](../advanced/chain-finalization.md) のような終了設計も含め、記録済みのデータ実体と検証根拠を保全します。終了設計そのものが既存の保存量を減らすわけではなく、その後も履歴を取得・復元・検証できる構成が必要です。

## チェーンが止まったら保存したデータはどうなりますか？

「停止」が、ブロック生成の停止なのか、履歴を提供するノードやAPIの停止なのかによって異なります。

| 停止しているもの | 記録済みデータへの影響 |
| --- | --- |
| 新しいブロックの生成 | 新たなトランザクションはブロックへ取り込まれませんが、必要な履歴を保持し、取得要求に応答するノードやAPIがあれば、記録済みデータは取得できます |
| 一部のノードや取得用API | その取得元は利用できませんが、同じネットワークの必要な履歴を提供する別の取得元があれば、取得を継続できます |
| 利用可能なすべてのノードや取得用API | それらを経由した取得はできません。保存済みの履歴やアーカイブがあれば、取得環境の復旧や別の読み取り手段による復元・検証を検討できます |

ブロック生成の停止やノードの停止だけで、保存済みの履歴が消えるわけではありません。重要なのは、データ実体を含む履歴が残っているか、それを読み出す手段があるか、検証に必要な根拠を参照できるかです。

チェーン履歴、対象ブロックの識別情報、ネットワーク識別情報、データ形式、検証手順、[BeaconとAnchor](../advanced/beacon.md) のような外部根拠を保全しておくと、元の取得サービスが終了した後の再検証に役立ちます。外部根拠だけではデータ実体を復元できないため、履歴やアーカイブ本体も必要です。計画的な停止・移行に備える方法は [Chain Finalization](../advanced/chain-finalization.md) を参照してください。

## ハッシュだけ保存すれば十分では？

ハッシュは、取得したデータが記録時の内容と一致するかを照合するための根拠になります。ただし、**変更を検知できることと、記録時のデータへ復旧できることは別です。**

ハッシュのみをチェーンに記録する方式では、不一致を検知しても、そのハッシュから元のデータを復元することはできません。別に保管したデータ実体やバックアップが失われたり、改ざん・暗号化されたりすると、変更を検知できても復旧できない可能性があります。

フルオンチェーンでは、データ実体と検証根拠を同じチェーン履歴に保持します。そのため、**変更の検知と、記録済みデータからの復元・再検証を一体として設計できます。** 手元のデータが変更・消失した場合にも、必要な履歴を取得できれば、そこから記録時のデータを復元し、記録との対応を確認できます。

この復旧性には、データ実体を含む履歴が残り、取得できること、対応する復元仕様やソフトウェアが利用できることが必要です。暗号化した記録では復号鍵も必要です。変更を検知しただけで必ず復旧できるという意味ではありません。

保存方式は、変更の検知だけでよいか、復旧元も検証根拠とともに残す必要があるかを含めて判断します。詳しくは [フルオンチェーンとは](../concepts/full-onchain.md) を参照してください。

## IPFSやArweaveのような外部ストレージと何が違いますか？

大きな違いは、**各ノードがどの範囲のデータを複製して保持するか**です。ネットワーク全体のノード数と、対象ファイルの復旧元になるコピーの数は区別する必要があります。

| 方式 | ノードによるデータの保持 |
| --- | --- |
| Symbol上のNFTDrive | チェーン履歴全体を保持する同期済みのフルノードは、トランザクションに格納されたファイル本体のデータ片も含めて複製する |
| IPFS | ノードごとに取得・保持するコンテンツが異なる。継続的な保持にはピン留めなどを使い、対象データを保持するノードを確保する |
| Arweave | ノードが設定した範囲のデータを同期・保持する。各ノードが必ず全データを保持する方式ではなく、全体を保持する構成も取り得る |

SymbolのPeerノードは処理した各ブロックをディスクへ保存します。NFTDriveのファイル本体はそのブロック内のトランザクションに含まれるため、履歴全体のフルコピーにファイル本体も含まれます。ここでいう「100%のコピー」は、同期した対象履歴全体を保持するという意味であり、すべての接続先が常に同期済みで、取得用APIも利用可能という意味ではありません。ノードとAPIの役割は [Symbol公式ドキュメント](https://docs.symbol.dev/concepts/node.html) を参照してください。

IPFSでは、対象ファイル全体を複数のノードへピン留めすることもできますが、ネットワークの全ノードへ自動的に複製されるわけではありません。Arweaveも、各ノードが保持する範囲を設定する方式なので、「IPFSやArweaveでは完全なコピーを持てない」という意味ではありません。詳しくは [IPFSの保持とピン留め](https://docs.ipfs.tech/concepts/persistence/) と [Arweaveの同期・保存構成](https://docs.arweave.org/developers/mining/overview/syncing-and-packing) を参照してください。

この違いは復旧元の考え方に関わります。Symbol上のNFTDriveでは、必要な履歴の完全なコピーが残っていれば、そこからファイル本体を復元し、記録との対応を検証できます。運用を評価するときは、対象データの完全なコピーがいくつあり、管理者や保存拠点が独立しているか、実際に取得できるかを確認します。フルオンチェーン一般がすべて同じ複製方式というわけではないため、利用するチェーンの実装と構成も確認してください。詳しくは [フルオンチェーンとは](../concepts/full-onchain.md) をご覧ください。

## フルオンチェーンは本当に必要ですか？

フルオンチェーンにする意味は、**データ実体そのものをチェーン上の記録と結び付け、取得・復元・照合を通じて検証できる状態にすること**です。データの大きさや保存年数によって、その意味が決まるわけではありません。

例えば、1文字のテキストでも、その文字を表すデータ実体をトランザクションに含めて記録すれば、後からどのバイト列が記録され、どのブロックに含まれるかを確認できます。短いメッセージや日常的な記録にも、データ実体と検証根拠を一体として残す意味があります。数十年の保存や特別な用途だけに限られるものではありません。

この検証可能性を長く引き継ぐには、データ実体と履歴を保持し、取得・復元できる運用が必要です。[DAOの運用](../advanced/dao-operation.md) のように、不特定多数の参加者が担い手を交代しながら記録を保持することで、永続性を目指す新しい組織の取り組みにもつなげられます。フルオンチェーンがデータにもたらす検証可能性と、それを継続させる運用を組み合わせる考え方です。

詳しくは [フルオンチェーンとは](../concepts/full-onchain.md) を参照してください。

## データは誰でも見られますか？

パブリックなブロックチェーンに平文で記録した内容は、原則として第三者が取得・閲覧できるものとして扱います。暗号化した場合も暗号文自体は取得できますが、内容を読むには対応する鍵や共有パスワードによる復号が必要です。

内容を閲覧できる相手を限定したい場合は、保存前の暗号化を検討できます。BEYONDデスクトップ版では、ファイル本体を暗号化して記録できます。操作と鍵の保全方法は [ファイルを暗号化する](../guide/file-encryption.md) を参照してください。

ただし、ファイル名や説明などのメタデータ、トランザクションの署名者・宛先まで自動的に非公開になるわけではありません。鍵や共有パスワードが漏えいすれば内容を読まれる可能性があり、復号に必要な情報を失えば、自分でも内容を復元できなくなる可能性があります。

また、第三者が保存した暗号文を後から回収・消去することはできず、将来の暗号解析や計算技術の進歩による復号リスクも残ります。記録前に、暗号化の対象と公開される情報、必要な機密保持期間、鍵の管理方法を確認し、そのリスクを許容できる情報か判断してください。

## 個人情報を保存できますか？

技術的には書き込めてしまいますが、**推奨しません**。

ブロックチェーンに記録されたデータは、原則として削除も修正もできません。個人情報保護の観点（削除請求への対応等)と本質的に相性が悪く、将来にわたって公開され続けるリスクがあります。個人情報や機微な情報は、チェーン上に記録しない設計を強くおすすめします。詳しくは [既知の制限](../reference/known-limitations.md) をご覧ください。

## 暗号化すれば安全ですか？

短期的には保護になりますが、長期的には注意が必要です。

チェーン上のデータは削除できないため、暗号化したデータは「いつか解読される可能性を抱えたまま公開され続ける」ことになります。暗号方式は時間とともに弱くなる可能性があり（計算能力の向上、新しい攻撃手法、量子計算機など）、数十年の時間軸では「現在の暗号化」が安全である保証はありません。

「暗号化すれば何を書いてもよい」とは考えず、そもそも公開されて困る情報は記録しない、という判断を優先してください。

## 100年後も検証できますか？

100年後の検証成功を保証することはできませんが、将来も検証できる可能性を高める設計はできます。そして、その価値は100年後だけでなく、記録直後から日常の利用、数年単位の運用や引き継ぎにもあります。

ファイル本体だけを保存する構成や、本体・履歴・検証根拠を別々に管理する構成と比べ、フルオンチェーンには次の利点があります。

- データ実体とトランザクション、ブロックの関係を同じ履歴からたどり、取得した内容が記録と対応しているか確認できる。
- 手元のデータの変更や消失に対し、必要な履歴が取得できれば、記録済みデータからの復元と再検証を一体として行える。
- サービスの終了や担当者・運営組織の交代時にも、データ実体と検証根拠をまとめて引き継ぎ、元のサービスとは別の環境で確認できる構成を作れる。

**検証、復旧、継承を一体として求める用途では、これらは従来の保存構成に対する大きな利点です。** 従来の方式でも署名、監査記録、バックアップなどを組み合わせて対応できますが、フルオンチェーンはデータ実体と記録根拠を同じ履歴に含めることを基盤にできます。容量や費用を含むすべての条件で、一律に優れるという意味ではありません。

100年という時間軸では、運用主体やネットワークの変化、暗号方式の安全性の変化、復元ソフトウェアの消失なども考慮します。[DAOの運用](../advanced/dao-operation.md) による継続的な保持・継承、[Chain Finalization](../advanced/chain-finalization.md) による終了・移行設計、[BeaconとAnchor](../advanced/beacon.md) による外部根拠を組み合わせ、必要なアーカイブ、仕様、ソフトウェアを保全します。現在から得られる利点を活用しながら、将来の再検証に必要な条件を維持していく考え方です。

## デスクトップ版とWeb版は何が違いますか？

記録やVerified Browserでの閲覧は両方で利用できますが、ファイル暗号化、WindowsのVerified Drive、LAN内ノードへの直接接続、ウィンドウを閉じた後の処理継続などはデスクトップ版の機能です。

詳しくは [デスクトップ版とWeb版](../guide/editions.md) をご覧ください。

## 暗号化したファイルをWeb版で開けますか？

共有パスワードが設定された対応形式と、旧形式の記録はWeb版でも開けます。記録アドレスの暗号化キーだけで保護されたファイルは、対応する暗号化キーを持つデスクトップ版が必要です。

復旧フレーズをWeb版や単体ビューアへ入力してはいけません。詳しくは [ファイルを暗号化する](../guide/file-encryption.md) を参照してください。

## バイナリ保存ならファイルサイズに上限はありませんか？

Base64全体文字列に由来する固定上限は回避できますが、任意サイズを保証するものではありません。端末のメモリ、暗号化・復号、ネットワーク、ノード、手数料などの制約は残ります。

保存モードごとの既知の制約は [記録サイズの制約](../reference/record-size-limits.md) を参照してください。

## Verified Driveの「検証済み」は何を意味しますか？

対象ネットワークとトランザクションを確認し、記録形式を復元したうえで、初回取得したバイト列のSHA-256とサイズをローカルの比較基準として保存したことを意味します。

このハッシュはTOFUの基準であり、初回取得内容が正しかったことを独立して証明するものではありません。詳しくは [Verified Drive](../guide/verified-drive.md) を参照してください。

## BEYONDは何を保証しますか？

BEYONDは、データ実体と記録情報の照合、ブロック・トランザクション・ネットワーク情報の確認、検証手順の分かりやすい提示、記録の根拠の確認を支援します。

一言で言えば、「検証可能性を人間が扱える形にすること」がBEYONDの提供範囲です。詳細は [BEYONDが保証すること / 保証しないこと](../concepts/guarantees.md) をご覧ください。

## BEYONDは何を保証しませんか？

チェーンの永続的な稼働、ノードの永続的なデータ保持、秘密鍵の紛失防止、不適切に記録された個人情報の安全性、外部システムの永続性、誤ったネットワーク設定で意図した対象を検証できることは、BEYONDの保証範囲外です。

これらはBEYONDの欠陥ではなく、検証ツールという役割の境界です。境界を明示することが信頼の前提だと考えています。詳細は [BEYONDが保証すること / 保証しないこと](../concepts/guarantees.md) をご覧ください。

## 独自チェーンでも使えますか？

はい。Network Profileに独自チェーンの情報（generationHash・networkType・epochAdjustment・ノードURL）を登録することで、独自チェーン上の記録の確認・検証に利用できます。

登録時には、generationHashが意図したチェーンのものと一致することを必ず確認してください。手順は [Network Profile](../guide/network-profile.md) をご覧ください。

## BNLとの関係は何ですか？

BNLは、NFTDriveのエコシステムにおける**独自ブロックチェーンの作成ツール**です。BEYONDは、BNLで作成したチェーンへ接続し、データの記録・取得・復元・検証に利用できます。

BNLとBEYONDは、「チェーンを作成するツール」と「そのチェーン上のデータを記録・利用・検証するアプリケーション」という役割分担です。BEYONDはBNLで作成したチェーンのほか、[Network Profile](../guide/network-profile.md) を通じて他の互換チェーン（テストネット・メインネット・独自チェーン）にも接続できます。
