# ネットワークを診断する

Blockchainsのネットワーク診断では、登録したチェーンのREST API、P2P接続、過去のブロックの提供状況、取得したブロックとREST基準の整合性を確認できます。データの取得先を選ぶときや、ネットワークの状態を調べるときに使います。

診断結果は、今回観測できた対象の実測値です。単一APIへの接続成功、ピア数、自己申告のロールだけでネットワーク全体を正常とは判定しません。通常のオンチェーンデータ取得・検証には引き続きRESTを使い、診断のP2P通信は独立した検査として実行します。

## 利用環境を確認する

| 環境 | 確認できること |
| --- | --- |
| デスクトップ版 | RESTの基本情報に加え、Catapult互換P2Pへの到達性、4地点のブロック提供、REST基準との整合性を検査する |
| Web版 | ブラウザーから取得できるRESTの実測値を記録する。P2Pへ直接接続せず、結果は `rest-only` になる |

Web版のREST接続には、HTTPSページからHTTPノードへの接続制限、CORS、プロキシなどの影響があります。接続条件は[デスクトップ版とWeb版](./editions.md)も参照してください。

診断は読み取り操作です。トランザクションの送信、ノードの自動修正、登録ネットワークの書き換えは行いません。デスクトップ版のP2P接続には診断時に生成する一時的な鍵と証明書を使い、ウォレットの秘密鍵は使いません。

## 診断を実行する

1. **Blockchains**を開き、診断したいネットワークのカードを確認する。
2. そのカードの**診断**を押す。
3. モーダルに表示される進捗を確認する。
4. 終了後、対象カードの**詳細 → 診断結果**を開く。

診断対象は、押したカードの設定を開始時に固定します。既定の保存先ネットワークを診断する操作ではなく、診断中に既定を切り替えても対象は変わりません。

進捗は「API接続 → 初期ピア → P2P探索 → 到達性 → 4地点履歴 → 集計・保存」の6段階です。探索中は検査対象の総数が未確定なので、完了率を表示しません。対象が確定すると検査件数から進捗を示します。

**診断を中断**を押すと進行中の通信を止め、その時点までの情報を保存します。ただし、終了時の追加照合・保存中は中断できません。アプリの強制終了や画面の破棄では、途中結果を保存できない場合があります。

| 実行結果 | 意味 |
| --- | --- |
| `complete` | デスクトップ版で診断処理が最後まで終了した |
| `rest-only` | Web版でRESTのみを観測した |
| `cancelled` | 利用者が診断を中断した |
| `error` | 利用できるAPIがない、ワーカーが失敗したなどの理由で診断を終えられなかった |

「診断完了」は処理が終わったことを示します。全ピアへの接続成功や、全項目の採点成立を意味しません。最後の段階が完了色になるのは `complete` かつローカル保存にも成功した場合です。保存に失敗した場合は画面の通知を確認してください。

## 診断結果を読む

結果には次の4タブがあります。

| タブ | 確認する内容 |
| --- | --- |
| 最新の診断 | 最新の実行結果と測定内容、品質評価とその対象日時 |
| 過去との比較 | 比較条件が揃った診断とのスコア差 |
| 履歴推移 | 保存済み診断の変化 |
| ピア詳細 | 各ピアの到達性、4地点の取得結果、整合性。分類フィルターで対象を絞れる |

### ノード数と成功数の意味

登録RESTノード、REST APIが返したピア候補、P2P探索で発見したピアは、それぞれ異なる集まりです。例えば登録RESTノードが20件でも、探索開始候補が最大8件、発見P2Pピアが最大40件になるため、数が一致しなくても異常ではありません。

「検査完了」は接続不能を含めて処理を終えた数です。進捗の「成功」は、到達性段階では接続成功、履歴検査段階では4地点の取得成功を指します。ブロックの整合性を確認できた `verified` 件数とは異なります。

### 4地点の履歴提供と整合性

診断開始時の現在高をHとして、およそ25%、50%、75%、100%の高さのブロックを要求します。正確には `floor(H/4)`、`floor(H/2)`、`floor(3H/4)`、`H` で、各高さの下限は1です。

各地点の結果は「取得成功」「提供不可」「未確認」を分けます。タイムアウトや通信エラーによる未確認を、提供不可や0点の証拠へ置き換えません。4地点すべてを取得できても、全履歴の保持や将来の提供継続を証明するものではありません。

取得後の整合性は、構造やヘッダーハッシュを検査し、信頼できるREST基準と照合して判断します。

| 整合性状態 | 読み方 |
| --- | --- |
| `verified` | 対応形式の構造・高さ・ネットワークとヘッダーハッシュを確認し、信頼できるREST基準と一致した |
| `mismatch` | 不一致または不正な構造を検出した。採点上の不一致として数えるには信頼できる基準との比較が別途必要 |
| `unverified` | 未対応形式、未確定の分岐候補などで検証が完了していない |
| `reference_unavailable` | P2Pブロックを取得できたが、比較できる信頼済みREST基準がない |

取得成功でも、整合性は未検証の場合があります。未確定高の差異には分岐の可能性があり、確定済みの差異でも基準APIやネットワークの追加調査が必要です。差異だけでノードの不正行為と断定しないでください。

## 品質スコアを読む

各軸は0.00～5.00点で、条件を満たさず評価できない軸は未評価になります。

| 軸 | 重み | 確認すること |
| --- | ---: | --- |
| 履歴可用性 | 35% | 応答を判定できた範囲で、4地点のブロックを提供できる割合 |
| 履歴冗長性 | 25% | 4地点すべてを提供できるピア数。十分な検査済み割合も必要 |
| P2P到達性 | 15% | 接続試験済みピアのうち到達できた割合 |
| ファイナライズ健全性 | 15% | 対応する暫定基準での確定高の進行、遅延、別APIとの整合性 |
| データ整合性 | 10% | 信頼済みREST基準との十分な比較に基づく一致率 |

総合点には、履歴可用性・履歴冗長性・データ整合性の3軸が必須です。いずれかが未評価なら総合点を表示しません。任意軸が未評価でも総合点が成立する場合は「参考値」とし、評価済みの重みの合計を採点カバー率として示します。

ランクはAが4.50以上、Bが3.50以上、Cが2.50以上、Dが1.50以上、Eが1.50未満です。未評価をEや0点と読み替えないでください。

履歴提供状況のバーは全発見ピアを分母にし、可用性の採点は判定済み応答を分母にします。40ピア中20ピアが4地点を提供し、残り20ピアが通信不明なら、提供バーは50%です。判定済み範囲の可用性が5.00点でも、冗長性に必要な75%の判定済み率を満たさず、総合点は未評価になります。灰色は未確認を表します。

ファイナライズの暫定基準は、チェーン識別と所定の設定が一致する**Symbol Mainnetのみ**に適用します。ネットワーク名だけでは適用せず、他のチェーンや設定不明の場合は未評価です。短時間に確定高が変わらないことや、現在高との差だけで停止と判断しません。この採点基準はBEYOND独自の初期プロファイルであり、Symbol公式の障害基準ではありません。

計算式と採点成立条件は[ネットワーク診断の判定仕様](../reference/network-diagnostics.md)を参照してください。

## 評価の有効性と観測充足度を読む

品質スコアは過去の測定結果です。時間経過で品質点そのものを減らすことはせず、別の「評価の有効性」で根拠の鮮度を示します。

| 根拠 | 鮮度100%の期間 | 要再診断・期限切れの目安 |
| --- | --- | --- |
| 完全診断、P2P・履歴・整合性 | 3日まで | 5日超～7日は要再診断、7日超は期限切れ |
| REST API | 6時間まで | その後低下し、24時間超は期限切れ |
| ファイナライズ採点根拠 | 10分まで | その後低下し、30分超は期限切れ |

有効性は表示時の現在時刻から計算します。総合品質点が未評価なら有効性も0%です。必須軸が期限切れなら「期限切れ」、完全診断または必須軸が再診断帯なら「要再診断」になります。任意軸やAPIだけが古い場合は「鮮度低下」であり、ネットワーク障害を意味しません。期限切れの品質点は過去の実測値として確認します。

詳細の**チェーンを観測**は軽量なREST観測です。REST根拠の鮮度と観測記録を更新できますが、P2Pの再検査や品質スコアの再計算は行いません。P2P・履歴・整合性・ファイナライズの品質サブスコアの検証日時も更新しません。古い品質評価を更新するには、改めて完全診断を実行します。

観測充足度は、直近30分を5分間隔の6枠に分け、観測できた枠数から求めます。同じ枠で繰り返しても1枠です。6枠すべてに観測があり、最初と最後が20分以上離れると「観測充足」になります。観測不足は監視密度の不足であり、確定処理の停止を示しません。採点カバー率や有効性%とも別の指標です。

常時監視やバックグラウンドでの定期実行はありません。詳細画面も自動更新ではなく、開く際に保存済みデータから再表示します。

## 中断・履歴・保存を確認する

最新の診断が中断・失敗・RESTのみで終わった場合、実行結果はそのまま残し、品質と有効性は同じチェーンの最後の完全診断を対象日時付きで表示します。中断で以前の評価を消すことはありませんが、以前の測定日時による鮮度低下は続きます。完全診断が一度もなければ未評価です。

新しい完全診断が終わると、点数が下がった場合や採点不能だった場合も新しい結果を採用します。良い過去の点数だけを選ぶ仕組みではありません。

診断履歴は最大20件、同じチェーンの最後の完全診断は別途1件保持します。比較・推移からは中断・失敗を除外し、採点版やチェーン識別、探索・検査条件が揃うときだけスコア差を表示します。候補の無作為選択により、再診断しても同じピアを検査するとは限りません。

保存先は利用中のブラウザーまたはデスクトップ版プロファイルのローカル保存領域です。端末間・ブラウザー間の自動同期はなく、保存領域を消去すると履歴と観測記録も失われます。旧履歴は可能な範囲で現行採点ロジックから再計算するため、将来のロジック変更後も表示点が不変とは限りません。

## 診断で確認できる範囲

探索は最大40ピア・2段で、接続・検査は最大4件ずつ並列に進めます。到達不能にはノード停止のほか、ファイアウォール、TLS非互換、時間切れなどの原因があります。発見できなかったことだけでネットワーク全体の断絶を証明できません。

ブロック整合性の確認には、署名の暗号学的検証、Voting Set、全トランザクションの実行や状態遷移、チェーン全体の合意の検証は含みません。公開鍵が異なっても、別事業者や別設備とは限りません。長期の可用性や事業者の独立性も、この診断だけでは確認できません。

関連する設定は[Network Profile](./network-profile.md)、取得元との関係は[BEYONDの信頼モデル](../concepts/trust-model.md)、詳細な条件は[ネットワーク診断の判定仕様](../reference/network-diagnostics.md)を参照してください。
