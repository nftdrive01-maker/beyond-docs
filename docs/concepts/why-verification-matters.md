# なぜ検証が必要なのか

データが画面に表示されていることと、その表示の根拠を利用者が確認できることは同じではありません。BEYONDが解決しようとしているのは、サービスの説明を信じるだけでなく、データ実体とチェーン上の記録の関係をたどれる状態を作ることです。

## Web画面だけでは根拠が残らない

一般的なWebサービスでは、画面の内容は運営者のデータベース、API、アプリケーションの実装に依存します。表示が正確であっても、利用者が取得元や計算過程を確認できなければ、独立した再確認は困難です。サービスの停止、仕様変更、画面の改変によって、後から同じ根拠へ到達できなくなることもあります。

ブロックチェーンを使う場合も、画面に「チェーンで確認済み」と表示するだけでは十分ではありません。どのネットワークの、どのノードから、どのトランザクションとブロックを取得し、何を照合したかが必要です。

## チェーンへの記録だけでも十分ではない

ハッシュだけをチェーンへ記録した場合、ハッシュは元のデータ実体を保持しません。照合対象となる実体が失われれば、ハッシュが残っていても内容を表示・利用できず、そのハッシュに一致するかも確認できません。

一方、データ実体がどこかに残っていても、それがどのトランザクションに対応し、どのブロックに含まれ、どのネットワークの履歴なのかを確認できなければ、チェーン上の記録との関係は判断できません。

必要なのは、次の要素を一つの検証経路として関連付けることです。

```text
データ実体 → ハッシュ・識別情報 → トランザクション → ブロック → チェーン → ネットワーク
```

## 停止後・移行後にも検証できる設計

検証が必要になるのは、サービスやチェーンが正常に動いている間だけではありません。運営サービスの停止、ノードの減少、別チェーンへの移行、ソフトウェアや暗号方式の世代交代の後に、過去の記録を確認したい場合があります。

そのため、稼働中のAPIだけに依存せず、次の情報を保全する設計が必要です。

- データ実体またはそれを復元できるチェーン履歴
- トランザクションとブロックの識別情報
- 対象ネットワークを特定する情報
- 取得元、取得時点、照合結果
- データ形式、暗号方式、検証手順
- 必要に応じて、アーカイブや外部に残した証明

これらを残しても、将来の取得や暗号方式の安全性を永久に保証することはできません。しかし、検証根拠がなければ再確認は始められません。保証できない条件を明示しながら、再検証できる可能性を高めることが重要です。

## BEYONDが目指すこと

BEYONDは、BEYOND自身の判定を無条件に信頼するよう求めません。保存されたデータやチェーン情報を取得し、識別情報や参照関係を照合し、どの検証条件を満たしたかを利用者が確認できる状態を目指します。

つまり、BEYONDが提供しようとするのは「正しい」というラベルではなく、次の問いに答えるための根拠です。

- データ実体はどこから取得できたか。
- 取得した内容はチェーン上の記録と一致しているか。
- トランザクションは対象ブロックに含まれているか。
- そのブロックは指定されたネットワークの履歴として確認できるか。
- 複数の取得元を使った場合、同じ情報が得られたか。
- どの範囲を確認でき、どの範囲は未確認か。

具体的な4段階は [検証可能なデータとは](./verifiable-data.md)、依存する前提は [BEYONDの信頼モデル](./trust-model.md) で説明します。
