# 特定のサービスに依存しない情報通信インフラ

BEYOND／NFTDriveが目指すのは、特定の事業者のサービスや単一の配信サーバーが動き続けることを必須としない、情報通信インフラの構築です。

コンピューターやサーバーが不要になるわけではありません。利用者や運用者がネットワークを構築し、必要な履歴を保持・提供することで、取得元を引き継ぎながらデータの取得・復元・検証を続けられる構造を目指します。

## 技術の役割分担

| 技術・構想 | 役割 |
| --- | --- |
| BNL | 独自ブロックチェーンを作成し、ネットワークを構築・運用するための技術・ツール |
| NFTDrive | データ実体をトランザクションへ分割し、オンチェーンに記録する技術 |
| BEYOND | データの記録・取得・復元・検証・活用を行う環境 |
| WEB5 | フルオンチェーン情報を閲覧・検証・活用する時代を表す、NFTDriveの構想 |

例えば、BNLで構築したネットワークへNFTDriveの形式で記録し、BEYONDから取得・復元して根拠を確認します。各技術は役割が異なり、BEYONDを導入するだけでノード運用や履歴保全まで不要になるわけではありません。

矢印は基盤から利用へつながる役割の関係を示します。WEB5は独立した技術層ではなく、それらを活用する構想です。図を選ぶと拡大できます。

WEB5は業界共通の確定した標準ではありません。[WEB5とは](./web5.md) で、このドキュメントにおける定義を説明しています。写真、文書、組織の活動記録、HTMLサイトなどが活用対象です。

## 取得元を選び直せる構造

通常のWeb配信では、指定された配信元が停止するとコンテンツを取得できない場合があります。必要なデータ実体と履歴を複数の独立したノードやアーカイブが保持・提供していれば、別の取得経路から復元し、記録との対応を照合できます。

サービス終了や事業者撤退だけでなく、災害、通信障害、サイバー攻撃も想定して設計します。拠点、管理者、認証情報、電源、通信回線を共有するノードは、同時に停止する可能性があります。分散構成という名称だけでなく、何が同時に失われ得るかを確認します。

[![拠点Aのノードが停止しても、拠点Bのノードや読み出し環境を確保したアーカイブから取得し、BEYONDで復元・照合・検証する構成例](/img/concepts/infrastructure-nodes.svg)](/img/concepts/infrastructure-nodes.svg)

矢印はデータを取得する経路を示し、自動切り替えや自動復旧を保証するものではありません。アーカイブは、保管されているだけで常時取得できるとは限らず、読み出し環境の確保が必要です。図を選ぶと拡大できます。

## 継続できる条件を残す

代替ノードがあるだけで復旧できるとは限りません。次の条件を運用計画へ含めます。

- 復元に必要な履歴とデータ実体を保持し、読み出せること
- 対象ネットワーク、トランザクション、ブロックを識別できること
- 記録形式、復元仕様、利用可能なソフトウェアを引き継ぐこと
- 暗号化した記録では必要な鍵を安全に保全すること
- 別経路からの取得・復元・照合を実際に試すこと

ハッシュや外部証明だけでは、失われたデータ実体を復元できません。また、複数の取得元で内容が一致していても、記録内容の真実性や過去の合意形成の正当性まで、それだけで保証するものではありません。

参加者が運用を引き継ぐ [DAOの運用](../advanced/dao-operation.md) と、期間を定めた運用や停止・移行に備える [Chain Finalization](../advanced/chain-finalization.md) は、継続性を異なる面から支える設計です。

## 導入を検討するには

まず [5分で体験するBEYOND](../guide/quickstart.md) で利用者側の流れを確認します。運用側では [ネットワークを設計する](../guide/network-design.md)、接続側では [Network Profile](../guide/network-profile.md) を参照してください。実現できる範囲は [既知の制限](../reference/known-limitations.md) と併せて判断します。
